# 智能体与工具（教学篇）

> 这个服务最有学习价值的部分：一个"会自己查数据再回答"的 AI 智能体是怎么搭起来的。

## 从"调模型"到"智能体"的差别

- **调模型**：`输入 prompt → 输出文本`。一次调用，模型只知道你喂给它的东西。
- **智能体（Agent）**：模型可以**决定调用工具**（查数据库、调 API），拿到结果后继续思考，循环直到能回答。

差别是本质的：调模型像"问一个博学但消息闭塞的朋友"；智能体像"给这个朋友配了一台能上网查资料的电脑"。

## ReAct：思考与行动的循环

ReAct = **Rea**son（推理）+ **A**ct（行动）。本工程用 LangGraph 的 `create_react_agent` 预制件实现：

```python
graph = create_react_agent(
    chat_model(),              # 大脑：决定下一步做什么
    tools=TOOLS,               # 手：四个查询工具
    state_modifier=SYSTEM_PROMPT,  # 人设与规则（system 提示）
    checkpointer=MemorySaver(),    # 记忆（多轮对话状态）
)
```

### 一次完整循环（用户问"我妈妈最近的体检报告有什么异常？"）

```
1. 模型读问题 + 系统提示
   → 思考："我需要先知道'妈妈'是哪个成员 id"
   → 行动：调 list_family_members()
2. 工具返回："id=102 姓名=林晓 关系=mother …"
   → 模型思考："妈妈是 102，查她的报告"
   → 行动：调 list_recent_reports(family_member_id=102)
3. 工具返回："report_id=603《林晓 2025年度体检》…"
   → 模型思考："要看指标明细才知道异常"
   → 行动：调 get_report_detail(report_id=603)
4. 工具返回："空腹血糖: 6.8mmol/L（参考 3.9~6.1）【偏高】…"
   → 模型思考："信息够了，组织回答"
   → 输出最终回复（不再含工具调用，循环结束）
```

**注意第 1 步**：模型没有瞎猜"妈妈"的 id，而是先查了家庭成员列表——这是系统提示里"先理解用户提到的是哪位家人，再查对应数据"引导出来的行为。**prompt 质量 = 智能体行为质量**。

## 工具协议：docstring 就是模型的说明书

```python
@tool
def list_recent_reports(family_member_id: Optional[int] = None) -> str:
    """列出体检报告摘要（最近 20 份，不含指标明细）。family_member_id 可选——
    指定成员则单查该成员；不传查全家。先用 list_family_members 拿到成员 id。"""
    ...
```

`@tool` 装饰器把普通函数变成智能体工具，模型看到的"工具描述"就是 **docstring 原文**。所以：

- 函数名 → 工具名（模型据此选择）
- docstring → 使用说明（模型据此判断"什么时候该用我"）
- 参数类型标注 → 模型填参数的格式约束
- 返回的 str → 喂回给模型的观察结果

**写好 docstring 是智能体工程里 ROI 最高的工作**——描述含糊，模型就会在该调的时候不调、不该调的时候乱调。

### 四个工具一览（tools/__init__.py）

| 工具 | 数据源（经 Nacos 发现） | 用途 |
|---|---|---|
| `list_family_members` | family 服务 | 确定查询对象（成员 id） |
| `list_recent_reports` | health 服务 | 报告摘要列表 |
| `get_report_detail` | health 服务 | 单份报告的指标明细 |
| `get_balance_sheet` | finance 服务 | 家庭资产负债 |

## 身份注入：ContextVar 的用法与意义

**问题**：工具要查"当前用户"的数据，但模型不能被允许指定查谁（否则一句"查 id=1 的数据"就越权了）。

**方案**：`member_ctx: ContextVar[int]`

```python
# 请求入口（api/open_agent.py）：JWT 验签拿到 memberId 后写入上下文
token = member_ctx.set(member_id)
try:
    result = await graph.ainvoke(...)    # 智能体整个执行期间，上下文里都有这个 id
finally:
    member_ctx.reset(token)              # 请求结束恢复，绝不泄漏给下一个请求

# 工具内部：读取（模型传的参数里根本没有 member_id 这个东西）
member_id = member_ctx.get()
```

- **为什么用 ContextVar 而不是全局变量**：并发安全。A 请求和 B 请求各自持有独立的上下文副本，互不覆盖；全局变量在并发下会串号；
- **为什么模型无法伪造**：member_id 根本不在模型的可见范围里（不在 prompt、不在工具参数）——身份在代码层流动，模型只在结果里看到"查出来的数据"。

**这是"智能体安全"的第一课：权限相关的参数永远从可信上下文注入，不经过模型。**

## 多轮记忆：checkpointer

`MemorySaver` 按 `thread_id`（=conversation_id）保存每个会话的消息历史：

```
会话 A（thread_id="conv-123"）：["我妈妈叫什么？"， "林晓"， "她最近报告有异常吗？"， ...]
会话 B（thread_id="conv-456"）：独立的历史
```

所以用户可以追问"那我爸呢？"——模型能从历史里知道"那"指的是查报告这件事。MemorySaver 存内存（重启即失），生产换 `SqliteSaver`/`PostgresSaver` 只改一个构造参数——接口相同，这是**策略模式**的直接受益。

## 流式输出：astream_events

```python
async for event in graph.astream_events(state, config, version="v2"):
    if event["event"] == "on_chat_model_stream":
        yield ("token", event["data"]["chunk"].content)      # 模型逐 token 吐字
    elif event["event"] == "on_tool_start":
        yield ("status", f"正在调用工具 {event['name']} …")   # 工具调用进度
```

LangGraph 把执行过程变成事件流：模型每生成一小段就发一个事件、每次调工具也发事件。我们把它转成 SSE 推给前端——用户既看到"正在查家庭成员…"的进度，又看到回答逐字出现。

## 系统提示（人设）设计要点

`SYSTEM_PROMPT` 四条规则各有用途：

1. "必须调用工具查真实数据，**禁止编造数值**"——压制模型幻觉（编数据）；
2. "先理解是哪位家人再查"——引导先调 list_family_members 确认对象；
3. "先给结论再给依据"——控制输出结构；
4. "健康话题最后提醒遵医嘱"——合规兜底。

写智能体系统提示的心法：**每条规则都在堵一个观察到的失败模式**，不是堆形容词。

## 沙箱降级的设计取舍

沙箱模式下智能体换成 `FakeMessagesListChatModel`（返回固定消息的假模型）而不是硬跑 ReAct——因为 ReAct 需要 `bind_tools`（把工具清单绑定给模型）能力，假模型没有。**降级要降到"形状一致、行为简化"**，不能让沙箱模式走出另一条代码路径导致测了等于没测。
