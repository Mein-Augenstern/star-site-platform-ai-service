# ai-service 架构总览（教学篇）

> 本文面向 Python 初学者：讲清这个微服务「在平台里扮演什么角色、由哪些部分组成、为什么这样切分」。

## 一句话定位

**star-site-platform-ai 是整个 star-site 平台唯一的 LLM（大模型）出口**——所有需要"AI 能力"的地方（报告解读、拍照识别、财务诊断、智能体对话）都调这个服务，业务服务（health/finance 等 Java 微服务）自己不碰模型。

### 为什么要把 LLM 单独拆一个服务

1. **AI 资产集中**：prompt（提示词）、模型选择、输出解析全部集中在一处管理，改 prompt 不用重新部署 Java 服务；
2. **技术栈各用所长**：Python 是 AI 生态的母语（LangChain/LangGraph 等框架首发 Python），Java 继续做业务——两种语言通过 HTTP 互调，各干最擅长的事；
3. **模型无关**：换模型厂商（智谱→OpenAI→DeepSeek）只改两个环境变量，全平台业务零感知。

## 在平台中的位置

```
┌──────────────┐   HTTP/R {code,data}   ┌─────────────────────┐
│ Java 微服务   │ ─────────────────────▶ │  ai-service (Python) │ ──▶ 智谱 GLM
│ health       │   /internal/ai/**      │  FastAPI + LangChain │     (OpenAI 兼容)
│ finance      │ ◀───────────────────── │                     │
└──────────────┘                        └─────────────────────┘
                                              ▲
用户/小程序 ──── 网关 JWT ──── /api/ai/agent/**（智能体对话，SSE 流式）
```

- `/internal/ai/**`：服务间内部端点（不经网关、无 JWT），Java 的 Feign 直接调用；
- `/api/ai/agent/**`：C 端智能体端点（经网关 JWT 鉴权，自己再验签拿用户身份）。

## 目录与包划分

```
star-site-platform-ai-service/
├── Dockerfile / requirements.txt    # python:3.11-slim 镜像 + 依赖清单
├── app/
│   ├── main.py          # FastAPI 应用：路由注册 + Nacos 注册生命周期
│   ├── config.py        # 配置：全部环境变量注入（12-Factor 原则）
│   ├── r.py             # 平台统一响应信封（与 Java R 对齐）
│   ├── llm.py           # LLM 模型工厂（ChatOpenAI，文本/视觉两种）
│   ├── schemas.py       # Pydantic 请求/响应模型（自动校验）
│   ├── nacos_register.py # 服务注册与心跳
│   ├── core/            # 基础设施
│   │   ├── security.py  #   JWT 验签（拿当前用户 id）
│   │   └── discovery.py #   Nacos 服务发现（调 Java 内部端点用）
│   ├── tools/           # 智能体的工具集（查家庭成员/报告/资产）
│   ├── agents/          # AI 能力实现
│   │   ├── assistant.py      #   ReAct 智能体（LangGraph + 记忆 + 流式）
│   │   ├── report_ocr.py     #   拍照识别（LCEL 链）
│   │   ├── report_interpret.py # 报告解读（LCEL 链）
│   │   ├── finance_diagnosis.py # 财务诊断（LCEL 链）
│   │   └── chat_graph.py     #   简单对话（LangGraph）
│   └── api/             # HTTP 端点（薄层，只做协议转换）
│       ├── internal.py  #   /internal/ai/** 服务间端点
│       └── open_agent.py #  /api/ai/agent/** 智能体端点（SSE）
```

### 分层规则（与 Java 服务同构，跨语言对齐）

```
api/（薄端点层）──▶ agents/ + tools/（AI 能力层）──▶ llm.py + core/（基础设施）
                                    │
                                    └──▶ Nacos 服务发现 ──▶ Java 微服务 /internal/**
```

- **api 层零业务**：只做「HTTP 参数 → 调能力函数 → 包 R 信封返回」，任何逻辑都不写在这层（与 Java 的 Controller 军规一致）；
- **agents 层是核心**：每个文件一个 AI 能力，prompt 定义在这里；
- **core 层可复用**：JWT/服务发现与业务无关，抽出来给所有能力用。

## 三个关键机制（初学者最容易问的）

### 1. 服务注册与发现（和 Java 怎么互相找到对方）

微服务间不写死 IP，通过 **Nacos 注册中心**按服务名路由：

- 启动时注册「我叫 star-site-platform-ai，地址 star-ai:8091」；
- 每 5 秒心跳证明存活（15 秒没心跳被标记不健康，30 秒被摘除）；
- 智能体工具调 Java 时反过来：查 Nacos 拿 `star-site-biz-health` 的健康实例地址。

### 2. 统一响应信封（R envelope）

所有出参都是 `{"code": 0, "message": "...", "data": ..., "retryable": ...}`——Java 侧的 Feign 切面统一检查 code 并翻译异常，两种语言用同一契约。

### 3. 沙箱模式

没配 API key 时自动降级：不调真实模型，返回带【沙箱模拟】标记的固定数据。**没有密钥也能跑通全链路**（开发/演示不被阻塞），这是所有 AI 服务都值得抄的容错设计。
